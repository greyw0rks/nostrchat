# NostrChat threat model

NostrChat encrypts conversation content in the browser and authenticates messages to Nostr public keys. Relays and the chat cloud cache receive ciphertext. Wallet operations use a separate, server-held NWC delegation: the application server can decrypt that delegated credential and exercise its granted wallet permissions. Message encryption and wallet authorization therefore have different trust boundaries.

This document describes the implemented browser client, Convex chat backend, and local Express backend. It does not certify a person, a wallet provider, a relay, or a payment purpose.

A local Nostr key is a real identity and can use an explicitly selected external WSS relay. It lives in tab memory until locked or replaced. Users create and keep a passphrase-encrypted backup before activating a new local identity. Alternatively, a compatible NIP-07 signer supplies public-key lookup, signing, and NIP-44 encryption/decryption. Discovery prefers compatible Connect providers and observes late injection. The client probes NIP-44, checks the provider's account before and after operations, snapshots signing requests, and verifies returned event fields and signatures against the original request. NWC and WebLN wallet capabilities do not substitute for this identity signer.

NIP-17 messages use an unsigned kind-14 rumor containing the sender, one conversation recipient, content, creation time, and a hash-derived message ID. Each intentional send includes a cryptographic nonce so identical messages sent in the same second remain distinct. The sender encrypts that rumor with NIP-44 and signs a kind-13 seal. NIP-59 adds an encrypted, signed kind-1059 gift wrap using a disposable outer key. Both the recipient and the sender receive their own wrap of the same rumor; the sender copy supports history and recovery. Seal and gift-wrap timestamps are independently randomized within the preceding two days using a cryptographic random source. Kind 13 identifies a seal; it is unrelated to NIP-13 proof of work.

On receipt, the client verifies a canonical copy of the signed gift wrap, checks its recipient, decrypts and verifies the seal, and binds the rumor's author to the seal's author. It requires a truly unsigned rumor, a matching rumor hash, one valid recipient, a safe timestamp, and bounded content. Untrusted getters, serialization hooks, and nostr-tools' verification cache cannot substitute different fields. This proves authorship by the Nostr key and membership in the conversation; contact aliases and an npub do not establish a person's real-world identity.

The following data reaches each storage boundary:

| Data | Browser/device | Chat backend or other service |
| --- | --- | --- |
| Nostr private key and backup passphrase | Local keys and passphrases are temporary memory values; signer-managed keys stay with the signer. An optional NIP-49 vault/file contains an encrypted local key. | The account, history, and outbox APIs do not receive a Nostr private key or backup passphrase. |
| Message text, invoice cards, and peer receipts | Plaintext is decrypted for display in memory. The persistent message cache contains only validated, owner-addressed gift wraps. | The relay and cloud history hold encrypted gift wraps plus public envelope metadata. |
| Profile, contact aliases/notes, and relay preference | Display name and contacts include plaintext local metadata; they are not an encrypted device address book. Explicit contact export contains those details in plaintext. | Cloud account sync contains NIP-44 ciphertext encrypted to the identity itself, with an owner-bound revision. |
| Retry outbox | A NIP-44 payload encrypted to self contains the exact recipient/sender wraps and their owner, peer, and rumor ID. | Cloud outbox stores that opaque ciphertext with an owner, ID, state, and timestamps. |
| Attempted payment recovery | Invoice facts, conversation/standalone reference, attempted time, and any confirmed preimage are stored only in NIP-44 self ciphertext. | The payment service separately keeps authenticated invoice, amount, payment hash, wallet reference, attempt, outcome, and settlement-proof records. These operational payment records are readable by the service. |
| NWC delegated wallet credential | The connection form uses it transiently; the browser does not persist the URI in localStorage or account/outbox data. | The gateway encrypts it at rest with AES-256-GCM, binding it to the NostrChat product and owner. The server decrypts it to call the wallet provider. |

A NIP-49 backup uses passphrase-based scrypt and authenticated encryption. Restore checks the Bech32 checksum, exact 91-byte version-2 structure, supported key-security byte, and scrypt work factor before invoking the KDF. This client accepts logN 14–16 and exports at 16. Password input is bounded; new backups require at least ten characters. Restored key bytes must form a valid Nostr key and match an expected account when one is supplied. Temporary key buffers are cleared, and destroying a local identity disables its cryptographic closures. These controls bound malicious-backup work; a weak passphrase remains vulnerable to offline guessing. A forgotten passphrase or lost Nostr key cannot be recovered by the chat server.

The synchronous local history reader salvages a bounded legacy cache, validates signatures and ownership, strips invalid/public/extra fields, and prunes it to the current limit. Cache corruption, blocked storage, or a quota failure does not prevent display of a valid received message. Encrypted-history import checks the entire owner-bound batch before writing it. Payment recovery deliberately has stricter failure behavior: an unreadable or unwritable recovery store blocks another attempted payment until the user checks the wallet. Saves are serialized per owner, retain unresolved attempts, and never downgrade confirmed proof.

Cloud account writes use optimistic revisions so a stale tab cannot silently overwrite another update. Cloud history accepts only signed kind-1059 NIP-44 envelopes with the authenticated owner as their sole recipient. Outbox ciphertext is immutable per owner and rumor ID; its state only moves from queued to published. On restore, the client decrypts the bundle, checks recipient/sender envelope destinations, and unwraps the sender copy to bind the ID, sender, and peer. A cloud published flag records the client's relay-confirmation state and provides no payment or read-receipt evidence.

The client uses one selected relay connection. It checks received events against the actual subscription filters, deduplicates event IDs, processes asynchronous receive callbacks in a bounded queue, handles EOSE/CLOSED, and ignores callbacks from replaced sockets. A pending publication reuses the exact signed envelope. After a lost acknowledgement or reconnect, the client retrieves that event ID before attempting a bounded resend; a valid matching echo/retrieval or positive ACK confirms the relay saw it. Disconnects and missing acknowledgements eventually yield an uncertain result instead of silently creating a new message. Retrying an envelope never invokes a wallet payment.

The current limits are finite caches and admission controls, not permanent-archive guarantees:

| Boundary | Implemented limit |
| --- | --- |
| Text and structured chat payload | 4,000 text characters; 18,000 UTF-8 payload bytes; BOLT11 input up to 12,000 characters; invoice descriptions up to 160 characters. |
| Browser event processing | 80,000-byte canonical signed event; 100,000-byte incoming relay frame; bounded tag counts, tag sizes, and dates. |
| Browser encrypted history | 500 envelopes and 2,000,000 bytes; legacy reads are bounded at 5,000,000 bytes. Message state retains at most 1,000 messages. |
| Relay subscriptions and publishing | 16 application subscriptions, 30 pending publications, a global 2,000,000-byte receive queue, and up to 500 queued events per subscription. Default publication budget is three sends and 45 seconds. |
| Local account/recovery plaintext before self encryption | 60,000 bytes for account/retry bundles and payment recovery. Recovery retains up to 32 unresolved and 32 recent confirmed records; unresolved records are not evicted to make room for a new payment. |
| Contacts | 200 contacts; 40-character names and 240-character notes. |
| Cloud history and outbox | History: 2,000 envelopes/2,000,000 bytes per owner. Outbox: 100 items/2,000,000 ciphertext bytes per owner. Pages contain 1–50 items. |
| Cloud ciphertext and envelope admission | Account/outbox ciphertext up to 88,000 characters; cached gift-wrap content up to 30,000 characters; a 96,000-byte chat request-body ceiling. |

Cloud admission is intentionally tighter than the browser's receive limit, so a valid larger external envelope can remain readable in the relay/device cache while cloud sync reports a limit failure. Cache deletion does not erase relay storage, a peer's copy, exported files, or durable payment attempts. Retention and availability of the selected relay remain the relay operator's policy; there is no automatic multi-relay redundancy.

HTTP identity authentication uses NIP-98 kind-27235 signatures tied to the exact URL, method, body hash, and a short freshness window, with server replay tracking. Each actual authentication request adds a cryptographic client nonce, while simultaneous requests for one owner share the same authentication operation. Authenticated chat and chat-wallet requests carry the captured X-Nostr-Pubkey; the backend requires it to match the session owner, and successful responses echo it. Browser guards check account/relay epochs and cancellation before and after asynchronous work. These checks prevent an old signer or HTTP completion from applying to a new account. Cancelling a browser request cannot undo a payment already accepted by a wallet.

The browser's lightweight BOLT11 decoder supplies encoding-derived display facts and explicitly reports signatureVerified:false. Before a payment review or wallet execution, the chat backend's signedBolt11 validator checks the checksum, framing, tagged fields, fixed whole-sat amount, and ECDSA signature. It requires exactly one payment hash and one description or description-hash field. If an n payee tag is present, the signature must verify against that compressed public key; otherwise the payee is recovered from the signature and the invoice's signing hash, then verified. A valid invoice signature authenticates the invoice to that payee key. It does not independently associate a Lightning node with a Nostr contact or certify a business or delivered service.

An invoice card's amount, hash, expiry, and known description must match the encoded invoice. For an h-only invoice whose original description/metadata is unavailable, the only opaque form is description:'' plus descriptionHash exactly equal to the encoded h value. The UI displays “Description unavailable.” It does not invent a human purpose for an LNURL metadata hash. Known non-empty descriptions must still hash-match.

The server creates an immutable payment review bound to the authenticated owner, exact BOLT11, amount, hash, network, invoice expiry, wallet public key, connection fingerprint, and connection version. Reviews expire within 90 seconds and require explicit confirmation. The service enforces wallet capability, network, and configured payment limits. Chat wallet credentials and records have their own namespace and endpoints; a company expense cannot bypass its independent approval path through chat payment APIs.

Before submitting a payment, the browser durably records an encrypted attempt marker. The backend atomically claims the payment hash before its single wallet pay invocation. Concurrent/repeated submissions return the recorded outcome and cannot create another invocation for that invoice. A changed identity or wallet invalidates the review. Provider errors, missing responses, or unverifiable proof leave a durable unknown result rather than resetting the claim. Confirmed outcomes require a matching payment hash/preimage and the recorded attempt/wallet reference, and do not downgrade later.

GET /api/chat/payments/:hash performs status-only recovery, including after invoice or review expiry. It uses the original wallet fingerprint and exact recorded invoice/amount before accepting a provider lookup proof. It never calls pay_invoice. Stored confirmed receipts remain available; unavailable/revoked wallets or inconclusive lookup leave the attempt uncertain. The Activity view exposes recovery after refresh and for expired invoices. Clearing a local recovery cache does not clear the backend claim or make a previously attempted invoice payable again. A browser backup, a server receipt, and a wallet's own transaction history serve different recovery purposes.

A peer receipt proves knowledge of a 32-byte preimage whose SHA-256 matches one payment hash. It does not prove an arbitrary amount, payment route, paying person, purpose, or service delivery, and it cannot set a global paid flag. The client binds receipt matching to the exact owner/peer conversation, reversed payer/payee message direction, invoice facts, and invoice rumor ID when provided. A legacy hash-only receipt is usable only when it selects one unambiguous matching invoice in that conversation. Wallet-verified settlement remains distinct from peer-shared preimage proof.

The server-held NWC delegation requires trust in the deployment operator as well as the wallet provider. The operator's encryption key can open stored delegated credentials, and a compromised server could exercise their granted methods despite browser review controls. Provider-side method restrictions, spending budgets, and revocation remain authoritative. Disconnecting removes the app's credential record; revoke the delegation in the wallet provider when access must end. The Nostr identity secret, NWC delegated secret, wallet-service public key, and Lightning invoice payee key are separate roles.

A compromised page, browser/OS, or malicious signer can expose decrypted messages and a local key in memory or misuse allowed signer operations. NIP-44 conversation encryption has no forward secrecy or post-compromise recovery: compromise of a participant's long-term key can expose recorded messages. Disposable gift-wrap keys and randomized timestamps reduce exposed sender metadata but do not provide a ratchet.

Relays can drop, delay, reorder, censor, replay, or correlate envelopes. They can see public recipient tags, subscription keys, IP/network information, size, and timing, and can cluster sender/recipient copies. A relay acknowledgement establishes relay receipt, not delivery, reading, or settlement. The application host also observes account access and payment operations. Encryption of chat caches does not conceal these transport and operational metadata.

The implementation is exercised by disposable local-key, protocol, relay-state-machine, storage-failure, authorization, invoice-signature, review/claim, and recovery regressions. These checks do not replace independent cryptographic or deployment auditing.
